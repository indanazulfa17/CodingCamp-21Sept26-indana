# Design Document: Expense & Budget Visualizer

## Overview

The Expense & Budget Visualizer is a zero-dependency, client-side web application delivered as a single HTML page. Users can record personal expenses (item name, amount, category), review them in a scrollable list, delete individual entries, watch a running total update in real time, and see spending distribution in a Chart.js pie chart — all without a server or build step.

All state lives in `localStorage` under the key `"transactions"`. The entire UI is driven by a single re-render cycle: whenever the transaction array changes, three UI regions (Balance Display, Transaction List, Chart) are updated synchronously within a single event-loop tick so they are always consistent with one another.

### Key Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| No framework | Vanilla JS | Requirement 6.4 — no build step; opens directly in browser |
| Single JS file | `js/app.js` | Requirement 6.2 — one JS file in `js/` |
| Single CSS file | `css/styles.css` | Requirement 6.1 — one CSS file in `css/` |
| Chart library | Chart.js via CDN | Requirement 5.6 — use Chart.js if available |
| Persistence key | `"transactions"` | Requirement 3.1–3.5 |
| Re-render strategy | Full re-render on every mutation | Simplest correct approach for small data sets |

## Architecture

The app follows a simple **unidirectional data-flow** pattern:

```
User Action (add / delete)
        │
        ▼
  Mutation Function       ← validates & mutates in-memory array
        │
        ▼
  persist(transactions)   ← writes serialized JSON to localStorage
        │
        ▼
  render()                ← redraws all three UI regions atomically
        │
        ├─▶ renderBalanceDisplay()
        ├─▶ renderTransactionList()
        └─▶ renderChart()
```

There is no two-way binding and no virtual DOM. Because the transaction list is expected to stay well under thousands of entries in a personal tracker, a full re-render on every mutation is fast enough to meet the 100 ms update requirement.

### Module Boundaries (inside `js/app.js`)

Although everything lives in one file, the code is organized into clearly separated logical sections:

```
js/app.js
├── Constants        — category definitions, localStorage key, limits
├── Storage          — load(), persist()
├── Validation       — validate(formData) → { ok, errors }
├── State            — in-memory `transactions` array
├── Mutations        — addTransaction(), deleteTransaction()
├── Rendering        — render(), renderBalanceDisplay(),
│                      renderTransactionList(), renderChart()
├── Chart Management — initChart(), updateChart()
└── Bootstrap        — DOMContentLoaded handler, form wiring
```

## Components and Interfaces

### 1. `index.html` — Page Structure

```
<body>
  <header>
    <h1>Expense & Budget Visualizer</h1>
    <div id="balance-display">…</div>
  </header>

  <main>
    <section id="form-section">
      <form id="input-form">…</form>
    </section>

    <section id="chart-section">
      <canvas id="spending-chart"></canvas>
      <p id="chart-placeholder" hidden>No data available</p>
    </section>

    <section id="list-section">
      <ul id="transaction-list"></ul>
      <p id="list-placeholder" hidden>No transactions yet</p>
    </section>
  </main>
</body>
```

### 2. Input Form (`#input-form`)

**Fields:**

| Field | Element | Constraints |
|---|---|---|
| Item name | `<input type="text" maxlength="100">` | Required, non-empty after trim |
| Amount | `<input type="number" step="0.01">` | Required, > 0, ≤ 999,999,999.99, ≤ 2 decimal places |
| Category | `<select>` | One of: Food, Transport, Fun |

**Behavior:**
- On submit, `validate(formData)` is called first.
- If invalid, inline `<span class="field-error">` elements are shown adjacent to each failing field; no transaction is created.
- If valid, the transaction is added, and the form is reset to its default state (`form.reset()`).

**Inline error elements** are pre-rendered in the HTML (hidden by default) and toggled via a CSS class; they are cleared on every fresh submit attempt before re-validating.

### 3. Transaction List (`#transaction-list`)

Each `<li>` entry is generated by `renderTransactionList()`:

```html
<li data-id="{id}">
  <span class="tx-name">{name}</span>
  <span class="tx-amount">{amount formatted}</span>
  <span class="tx-category">{category}</span>
  <button class="tx-delete" aria-label="Delete {name}">×</button>
</li>
```

- Rendered in reverse insertion order (most-recent first).
- The empty-state placeholder (`#list-placeholder`) is shown when the list is empty, hidden otherwise.
- Delete buttons are wired via **event delegation** on `#transaction-list` to avoid re-attaching listeners on every render.

### 4. Balance Display (`#balance-display`)

- Located inside `<header>` so it is always visible above the fold.
- Displays total formatted to two decimal places (e.g., `$1,234.56`).
- Shows `$0.00` when there are no transactions.
- Updated by `renderBalanceDisplay()` which sums `transactions.map(t => t.amount)`.

### 5. Pie Chart (`#spending-chart` / Chart.js)

- A single `Chart` instance is created on init and **updated** (not destroyed/recreated) on every render via `chart.data = …; chart.update()`.
- Categories with a zero total are excluded from `data.datasets[0].data` and `data.labels`.
- Category colors are fixed constants (see Data Models).
- When `transactions` is empty, the `<canvas>` is hidden and `#chart-placeholder` is shown.
- Chart.js is loaded from CDN; if it fails to load, a fallback message is displayed instead of the canvas.

## Data Models

### Transaction Object

```js
/**
 * @typedef {Object} Transaction
 * @property {string} id        — UUID v4 generated at creation time (crypto.randomUUID())
 * @property {string} name      — Item name, 1–100 characters, trimmed
 * @property {number} amount    — Positive float, max 2 decimal places, ≤ 999,999,999.99
 * @property {string} category  — One of: "Food" | "Transport" | "Fun"
 * @property {number} createdAt — Unix timestamp (Date.now()) at creation
 */
```

### localStorage Serialization

```js
// Write
localStorage.setItem("transactions", JSON.stringify(transactions));

// Read
const raw = localStorage.getItem("transactions");
const transactions = raw ? JSON.parse(raw) : [];
```

On read, each entry is validated. Any entry failing validation (missing name, non-positive amount, invalid category) causes the **entire stored collection** to be discarded, an error is logged to `console.error`, and the app initializes with an empty array.

### Category Color Map (constants)

```js
const CATEGORY_COLORS = {
  Food:      "#FF6384",
  Transport: "#36A2EB",
  Fun:       "#FFCE56",
};
```

Colors are consistent across renders because they are keyed by category name, not by array index.

### Validation Rules

```js
const RULES = {
  name:     { required: true, maxLength: 100 },
  amount:   { required: true, min: 0.000001, max: 999_999_999.99, maxDecimals: 2 },
  category: { required: true, values: ["Food", "Transport", "Fun"] },
};
```

`validate(formData)` returns `{ ok: boolean, errors: { name?, amount?, category? } }`.

## Correctness Properties

*A property is a characteristic or behavior that should hold true across all valid executions of a system — essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.*

### Property 1: Serialization round-trip preserves all transactions

*For any* array of valid Transaction objects, serializing the array to JSON and deserializing it back should produce an array that is deeply equal to the original (same ids, names, amounts, categories, and timestamps).

**Validates: Requirements 3.1, 3.2, 3.3**

---

### Property 2: Balance equals sum of all transaction amounts

*For any* non-empty collection of transactions, the value shown in the Balance Display shall equal the arithmetic sum of each transaction's amount, formatted to two decimal places.

**Validates: Requirements 4.2, 4.5**

---

### Property 3: Validation rejects all-whitespace names

*For any* string composed entirely of whitespace characters (spaces, tabs, newlines), submitting it as the item name shall be rejected by the Validator and no Transaction shall be created.

**Validates: Requirements 1.4, 1.5**

---

### Property 4: Validation rejects out-of-range amounts

*For any* numeric amount that is ≤ 0 or > 999,999,999.99 or has more than two decimal places, the Validator shall reject it and no Transaction shall be created.

**Validates: Requirements 1.4, 1.5**

---

### Property 5: Chart slice proportions sum to 100%

*For any* non-empty collection of transactions, the sum of all pie chart slice percentages (each computed as `categoryTotal / grandTotal × 100`) shall equal 100 (within floating-point rounding tolerance of ±0.01).

**Validates: Requirements 5.1**

---

### Property 6: Zero-amount categories produce no chart slice

*For any* transaction collection where a specific category has no transactions (total = 0), that category shall not appear as a slice in the rendered chart.

**Validates: Requirements 5.7**

---

### Property 7: Add then delete returns to original state

*For any* transaction collection, adding a transaction and then immediately deleting that same transaction (by its id) shall produce a collection equal to the original (same length, same contents, same order).

**Validates: Requirements 2.5, 3.1, 3.2**

---

### Property 8: Transaction list renders in most-recent-first order

*For any* sequence of N transactions added in insertion order, the Transaction List shall render them in reverse insertion order (most recent at index 0).

**Validates: Requirements 2.1, 3.3**

## Error Handling

| Scenario | Behavior |
|---|---|
| `localStorage` data fails JSON parse | `console.error` the error; initialize with empty array; app continues normally |
| `localStorage` data parses but contains invalid entries | `console.error` a validation message; discard the entire collection; initialize with empty array |
| Chart.js CDN fails to load | Hide `<canvas>`; show a static fallback message in `#chart-placeholder` |
| `crypto.randomUUID()` not available (old browser) | Fallback to a timestamp + Math.random composite ID |
| Form submitted with invalid data | Show inline field errors; do not mutate state; do not call `persist()` |
| Amount with > 2 decimal places entered | Validator rejects with error message; no transaction created |

## Testing Strategy

Because this is a client-side Vanilla JS app with no build step, the primary testing approach is:

### Unit Tests (logic layer)

The `validate()`, `persist()`/`load()`, and balance/chart computation functions are pure or near-pure. They should be extracted into testable units and covered with:

- **Example-based tests** for specific known-good and known-bad inputs.
- **Property-based tests** (using a library such as [fast-check](https://github.com/dubzzz/fast-check)) for the universally quantified properties defined above.

Each property-based test should run a minimum of **100 iterations** and reference its design property using the tag format:

```
// Feature: expense-budget-visualizer, Property 1: Serialization round-trip
```

### Integration / Manual Tests

Since the full render cycle involves the DOM and Chart.js, the following should be verified manually or with a browser-based test harness:

- Form submission with valid data adds a list item, updates balance, and updates chart.
- Form submission with invalid data shows inline errors and leaves state unchanged.
- Deleting a transaction removes it from the list, updates balance, and updates chart.
- Refreshing the page restores all transactions from localStorage.
- Corrupt localStorage data initializes with an empty state and logs to console.
- Empty state shows placeholders in the list and chart areas.
- All interactions complete within 100 ms (verified by performance.now() timestamps in development).

### Accessibility and Cross-Browser Checks

- Verify 4.5:1 contrast ratio using browser DevTools or an automated checker (e.g., axe).
- Confirm keyboard navigation through the form and delete buttons.
- Smoke-test in Chrome, Firefox, Edge, and Safari stable releases.
